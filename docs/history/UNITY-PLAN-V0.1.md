文档状态：开发建议稿；工程实现与平台验收尚未执行。

## 二十五、第一批 Codex 开发任务

### 25.1 V0.1 的目标与边界

第一阶段先证明两件事：底层世界能持续、可靠地演化；玩家能与一个有目标、有记忆的 NPC 形成值得回想的经历。

首个版本的完整体验仍然是：创建角色，在坊市获得修炼机会，从凡人成为炼气修士，与 NPC 相识并组队探索，经历战斗、约定和关系变化，闭关后看到世界继续发展，最后尝试筑基。

| 项目 | V0.1 范围与状态 |
| --- | --- |
| 引擎与工程 | 按原计划使用 Unity 6 LTS；M0 锁定具体补丁版本和依赖版本 |
| 初始世界 | 约 40 名 NPC；100 名 NPC 用于模拟测试 |
| 地点 | 保留区域、地点、势力的数据结构；首先制作一个测试坊市 |
| 探索内容 | 建议一处最小秘境，用于人物故事与战斗闭环 |
| 境界 | 凡人、炼气、筑基；首轮试玩后再讨论金丹 |
| 队伍 | 最多三人，主角手动、NPC 自动，支持自动战斗 |
| 关系 | 好感、信任、吸引；关系标签与可追溯记忆 |
| 重点人物 | 先完整实现一个重点 NPC 的故事分支 |
| AI | 第一阶段只接自由交涉，由规则系统决定能否生效 |
| 美术 | 已确认古风像素场景、简化像素行走角色、精细非像素古风人物立绘；开发前期使用占位素材 |
| 突破失败 | 已确认不致命，可损失修为，严重时可能跌境；幅度、概率与恢复规则待定 |
| 游戏模式 | 保留简单／复杂选择；复杂模式在其他场景真正死亡后本局结束；其余差异按待定项处理 |
| Mod | 建议本版做好内容数据与代码分离、稳定内容 ID 和版本记录；完整 Mod 加载与工具链另排任务 |

“先把底层世界跑通”允许使用调试窗口、文本列表和临时按钮。正式地图、美术数量、技能数量均不作为早期进度指标。

### 25.2 先固定六条工程约定

以下六条为本次建议的工程基线，目的是让各里程碑能够接续开发。

**1. 世界只有一份权威状态。**

角色状态、所在地点、势力归属、物品和关系以世界数据为准。Unity 场景中的小人、人物面板和 AI 对话读取这份状态，通过应用层提交操作。不能由不同界面各自维护一份 NPC 属性。

玩家与 NPC 复用修炼、物品、战斗和关系规则。玩家的差异主要是输入控制、专属法宝，以及模式规则明确允许的特例。

**2. 明确确定性的条件。**

同一个初始世界的复现条件是：世界 Seed、生成器版本、规则版本、内容版本、生成配置均相同。初始世界指玩家介入前的生成结果，玩家姓名与资质等创建输入单独保存。

将世界生成、角色资质重掷、世界演化、战斗结算、美术表现的随机源分开。资质可以无限重掷，但重掷次数不能消耗世界生成的随机序列。重掷序号和选中结果进入角色数据。

随机算法及版本固定；需要续跑的随机状态进入存档。实体和事件使用稳定 ID，规则遍历使用明确顺序。核心规则不以系统日期、帧率或无序集合遍历结果决定结算。

核心数值建议优先使用整数或固定精度表示。这里保证的是逻辑状态一致，画面帧序列不纳入世界确定性验收。重新请求 AI 得到的文本与提议也不纳入同 Seed 保证；已接受的提议须记录为确定的游戏操作。

**3. 游戏时间由一处推进。**

建议 V0.1 先采用日级世界模拟。交谈、修炼、赶路、探索、闭关分别通过配置声明时间成本。场景内走路与世界旅行分开处理。

建议临时采用“坊市内行走、浏览面板不推进天数；有明确耗时的行动提交后统一结算”的交互规则，正式节奏待试玩调整。退出游戏期间不自动按现实时间推进世界，除非后续另立需求。

推进 30 天与逐日推进 30 次必须遵守相同结算规则。闭关可以分批计算来保持界面响应，但玩家状态和 NPC 状态始终落在同一个已提交时间点。

**4. 事件记录先于复杂关系系统。**

从第一次修炼、交往和冲突开始，就产生结构化世界事件。事件至少包含事件 ID、游戏时间、参与者 ID、类型、地点、结果和关联原因。

游戏事实、NPC 记忆、调试日志分别承担不同用途：事实保存实际发生的事；记忆表示某个 NPC 经历或获知的内容；日志用于排错。关键承诺、履约、违约和死亡事件属于存档的一部分，不能随调试日志清理。

本版建议采用“世界快照＋关键事件记录”，只保存必要的行动进度与待处理事件；完整事件溯源框架和每次修炼都永久留档不属于当前必需工作。

**5. 存档要能恢复后续运行。**

存档不仅恢复人物面板，还要恢复游戏时间、随机状态、NPC 行动进度、待处理事件、物品归属、队伍、承诺、关系和关键记忆。

存档头记录结构版本、构建版本、规则与内容版本。JSON 先写临时文件，验证后替换正式文件，并保留一个已知可读的备份。加载时先检查版本及引用完整性，通过后才切换当前世界。

优先在完整行动或整日结算结束后存档。V0.1 建议暂不承诺战斗中途或半日结算中的任意存档。遇到不支持的版本应提示，而非静默重建或覆盖原存档。

**6. 普通按钮和 AI 使用同一条执行路径。**

所有会改变世界的操作都先形成请求，经规则校验后统一提交；提交成功才产生结果事件。失败操作不得留下半扣物品、半组队或只改变一方关系的状态。

AI 负责理解自由输入和提出建议。事实、资格、数量、收益、成功率与最终写入由游戏规则决定。

### 25.3 Milestone 0：工程骨架与最小基础设施

**目标：**建立能编译、能测试、能存读档的空白工程。

**实现内容：**

1. 创建 Unity 6 LTS 项目，在 `ProjectVersion.txt` 锁定具体版本，保存包清单及锁文件。
2. 初始化 Git，配置 Unity `.gitignore`，提交资源对应的 `.meta` 文件，采用适合版本管理的文本序列化设置。
3. 建立以下分层，并用程序集引用明确依赖边界。

| 层 | 职责 | 依赖约束 |
| --- | --- | --- |
| Core | 角色、世界、修炼、关系等纯逻辑与规则 | 不引用 UnityEngine、文件系统或网络实现 |
| Application | 创建角色、推进时间、组队、存读档等用例及服务接口 | 引用 Core |
| Infrastructure | JSON、文件、日志输出、AI Provider 等接口实现 | 按需要引用 Application 与 Core |
| Unity | 场景、输入、UI、动画、资源适配与启动装配 | 普通界面通过 Application 操作；启动入口负责装配实现 |

4. 配置 EditMode 与 PlayMode 测试。规则主要放 EditMode；输入、场景装配及 UI 集成放 PlayMode。Unity Test Framework 支持这两类测试及目标平台测试，具体版本随项目锁定。[Unity 测试框架说明](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/index.html)
5. 建立统一日志接口，记录级别、模块、操作 ID 与游戏时间；API Key 等凭证禁止写入日志和游戏存档。
6. 实现稳定 ID、Seed 与随机源接口、最小游戏时钟和事件记录结构。
7. 用一个极小测试状态完成 JSON 写入、读取、版本检查和损坏回退。
8. 提供 README：版本、打开步骤、测试步骤、存档位置及已验证环境。

**验收：**

- Mac 从干净检出打开项目，编译通过，EditMode／PlayMode 测试执行完成并保留结果。
- 最小状态经过写入与读取后核心字段一致；损坏存档不会覆盖可用备份。
- 相同随机种子生成相同测试序列；保存随机状态后续跑结果一致。
- Core 的规则代码无需场景和 MonoBehaviour 实例即可测试。
- Parallels 单独做一次兼容性验证，记录宿主芯片、Windows 架构、Unity 版本、启动和测试结果。保留原计划的验证目标，不预写“已支持”。Unity 官方给出的支持条件是原生运行环境，因此实际兼容结果需要本机验证。[Unity 6.0 系统要求](https://docs.unity3d.com/6000.0/Documentation/Manual/system-requirements.html)

Mac 工程验收与 Parallels 兼容性结果分项报告。兼容性未通过时明确标记阻塞及现象，再决定适用的辅助开发环境。

### 25.4 Milestone 1：角色创建与完整恢复

**目标：**创建出的角色能够退出、重开并准确恢复。

**实现内容：**

- `PlayerProfile`、稳定角色 ID、姓名、男女选择、外貌配置及外貌 Seed。
- 资质生成、无限重掷、重掷序号及选中结果。
- 三件专属法宝三选一，以内容 ID 保存选择。
- 简单／复杂模式选择，创建后保存模式配置版本。
- 基础创建校验与临时 UI。
- 创建确认后生成一次有效存档，重复点击不会重复发放法宝。

三件法宝的名称和效果如已有完整定案，按定案实现；当前记录未提供具体内容，先允许显式标识的测试配置完成选择与保存。正式展示前补齐，不能把临时效果写成已确认设定。

**验收：**

- 创建角色、退出应用、重新启动、加载，姓名、外貌、资质、法宝、模式完全一致。
- 多次重掷不消耗世界生成使用的随机源；用独立随机序列测试即可验证。
- 重复保存加载不重新掷资质、不重复发法宝。
- 未完成创建的数据不被当成可继续游戏的正式存档。

### 25.5 Milestone 2：确定性世界生成

**目标：**生成可复现、引用完整、基础关系合理的初始世界。

**世界至少包含：**区域、地点、势力、约 40 名 NPC、初始关系、游戏时间、世界 Seed 和版本信息。物品、队伍、记忆等状态随对应里程碑加入统一存档。

**NPC 最小字段：**

| 分类 | 字段 |
| --- | --- |
| 身份 | NPC ID、姓名、性别、出生游戏日／年龄、外貌 Seed |
| 修士状态 | 资质、境界、修为、存活状态 |
| 社会位置 | 所属势力 ID、当前位置或旅途状态 |
| 行为动机 | 性格、个人目标、当前行动及其进度 |
| 社会关系 | 关联角色 ID、关系类型、初始事实依据 |

采用分阶段生成：先创建区域、地点和势力，再创建 NPC，最后生成关系并统一检查引用。各类 ID 稳定产生；角色死亡后仍保留可供历史引用的身份记录。

师徒关系的合理性需要结合拜师时间、境界与传授资格；修仙世界中师父比徒弟年轻可能合理，不能只用年龄大小判错。具体资格未定时使用明确的测试规则，例外必须有设定依据。

**验收：**

- 同版本、同内容配置、Seed 12345，多次生成后的规范化核心状态摘要一致；比较时忽略日志时间、文件路径等环境字段。
- 固定另一组 Seed 的测试世界出现可解释的初始差异。
- 每个在世角色有且仅有一个有效位置状态；旅途中角色使用唯一旅途状态，不同时占据起点与终点。
- 势力、地点、关系端点均指向有效 ID；没有自我拜师等违反当前规则的关系。
- 初始世界保存再加载，摘要一致。
- 补做与 M1 的集成验收：同版本、同世界 Seed 下，资质重掷前后生成的初始 NPC 与地点一致。

### 25.6 Milestone 3：时间、最小修炼规则与 NPC 演化

**目标：**世界在没有玩家干预、没有大模型调用的情况下，自行推进并保持一致。

本阶段拆为三个子任务，以补齐原计划中 M3 依赖 M7 的问题。

**M3A：统一时钟与逐日调度。**

- 实现推进一天、推进指定天数及调试世界摘要。
- 建议固定每日处理顺序：到期状态及寿命检查 → 旅途抵达与行动资格检查 → 行动提案 → 共享资源冲突裁决 → 行动与遭遇结算 → 关系后果 → 不变量检查与日末提交。
- 每个阶段采用明确的快照、稳定排序和提交规则；共享目标的争用应有裁决，不能由集合遍历顺序决定。
- 死亡一经提交，后续阶段立即取消该角色行动；日末保留完整有效状态。

**M3B：玩家与 NPC 共用的修炼最小规则。**

- 提前实现修为增加、境界条件、突破判定、成功结果与失败结果。
- 凡人、炼气、筑基使用同一组规则接口；先采用显式的测试参数。
- 突破失败不致命；损失修为与跌境的数值、幅度按可替换配置实现。
- M7 在同一规则上补闭关、丹药、护法与玩家操作，避免再写一套修仙代码。

**M3C：有限规则驱动的 NPC 行为。**

- 根据目标、状态和资源，选择修炼、移动、交往或冲突等有限行动。
- 以简单规则或优先级驱动，行为理由可以在调试界面查看。
- 交往、冲突、突破和死亡从此阶段产生结构化事件；M4 再丰富关系与记忆。
- NPC 冲突先做共用的最小遭遇结算和结果接口；M6 扩展战斗时接入该接口。
- NPC 死亡的具体来源使用明确配置；寿尽、冲突等测试原因不得混同于突破失败。

**验收：**

建立固定 Seed 回归集，运行 100 名 NPC、3650 个游戏日。长模拟每个结算点都执行必要的不变量检查，不能只看最后一天。

- 死亡角色不再修炼、移动、组队或突破，但身份与历史仍可查询。
- 角色位置唯一；任务、行动的势力资格在执行时仍有效。
- 离宗、死亡、目标失效会取消或转移相关行动，处理原因留痕。
- 资源数量合法，修为处于有效范围，历史与关系引用不悬空。
- 突破失败不会直接产生死亡结果。
- 同一快照执行同一组操作，结果一致。
- 连续模拟 100 天，与模拟 40 天后存读档、再模拟 60 天，核心状态、随机状态和关键事件一致。
- 推进 30 天与调用 30 次推进一天，结果一致。
- 失败时报告 Seed、版本、出错游戏日、相关实体和最近事件，能从测试夹具复现。

记录长模拟耗时与内存作为基线；性能门槛在目标 Mac 实测后确定。当前约 40 名 NPC 优先使用简单单线程模拟，暂不为假设中的万人世界增加复杂调度。

### 25.7 Milestone 4：关系、承诺与可追溯记忆

**目标：**玩家和 NPC 的关系变化有事实依据，并影响未来行为。

**实现内容：**

1. 好感、信任、吸引三个维度。建议按 A 对 B 与 B 对 A 分别保存，避免默认双方感受相同。
2. 朋友、挚友、敌对、仇人、恋人、道侣、夫妻等关系标签。
3. 世界事件、NPC 记忆、共同经历与承诺记录。
4. 从事件到数值变化、再到行为条件的明确规则。
5. 人物面板展示最近关键经历与关系变化原因。

关系标签建议拆成可组合的社会关系与需要显式建立的亲密关系。哪些标签互斥、谁需要双方同意、恋人与道侣及夫妻是什么关系，应列出状态转换表；具体产品规则尚待确认。不能仅因吸引达到阈值就自动结婚。

记忆至少记录原事件 ID、知晓者、知晓来源、相关对象和长期重要性。NPC 的判断依据限于其经历或获知的事实，不能自动知道世界里所有人的秘密行为。

承诺至少包含双方、对象、履行条件、触发时间或期限、当前状态和来源事件。建议区分待履行、已履行、违约、取消及客观无法履行，防止将“秘境没有掉落凝元草”直接判成玩家违约。

**示例：**

| 游戏时间 | 世界事实 | 可产生的后果 |
| --- | --- | --- |
| 第 12 日 | 玩家在秘境救下某 NPC | 对方记住救助，按规则增加好感／信任 |
| 第 15 日 | 双方约定本次秘境获得的第一株凝元草归 NPC | 建立有条件的战利品承诺，暂不转移物品 |
| 第 18 日 | 凝元草已获得，玩家将其交给 NPC | 承诺履行，产生可追溯的信任变化 |
| 第 18 日，另一分支 | 玩家将约定物品据为己有 | 承诺违约，影响下次同行或分配条件 |

**验收：**

- 关系变化能追溯到具体事件及规则，而不仅是一组数值。
- 相同事件重复处理不会重复加减关系。
- 不知情 NPC 不会无依据地产生针对该事件的记忆。
- 承诺、关系、记忆存读档后保持一致。
- 数值、标签和实际行为一致：拒绝同行能够解释具体原因。

### 25.8 Milestone 5：最小地图与人物互动

**目标：**让底层世界第一次通过可操作场景呈现出来。

制作一个测试坊市，使用占位像素素材。完成玩家行走、碰撞、NPC 场景内移动、靠近后按键互动，以及人物界面。

人物界面显示：立绘占位、姓名、境界、关系、近期关键经历与互动按钮。

逻辑地点 ID 决定 NPC 是否存在于该坊市场景；场景坐标负责地点内的行走表现。NPC 离开坊市或死亡时，场景对象按世界事件同步更新。若位置影响可交互资格，需要在应用层验证，不能只依赖 UI 按钮是否亮起。

**验收：**

- 行走与碰撞有效，互动范围和界面开关正常。
- 场景显示的 NPC 与世界位置记录一致，离场和死亡及时反映。
- 打开人物界面读取真实数据；互动结果通过应用层写入世界。
- 切换场景和读档不重复生成同一 NPC。
- 场景内移动遵循已采用的时间规则，不意外多推进一天。

### 25.9 Milestone 6：轻量战斗与结算

**目标：**三人探索能够完成一次战斗，并把结果准确带回世界。

保留原定范围：最多三人队伍、主角手动、NPC 自动、自动战斗；普攻、四个技能槽、防御、丹药、撤退、胜负和掉落。先使用少量技能和简单敌人。

战斗采用回合、行动条或即时制，当前记录未说明；这是 M6 开工前要明确的交互决定，不从“四个技能槽”推断战斗形式。

本阶段补齐最低限度的基础属性、背包、物品数量、战斗结果与战利品池。境界提供的战斗属性来自共用角色规则；丹药扣除与掉落归属都由规则结算。

战斗场景输出确定的结果，由应用层一次性写回生命／伤势、消耗品、队伍变化、时间成本、掉落和关系事件。存在分配承诺时，战利品先进入待分配状态，不能直接全部进玩家背包。

**验收：**

- 队伍不会超过三人；死亡或不具资格的角色不能加入或继续行动。
- 手动与自动模式使用同一套合法行动及消耗规则。
- 撤退、失败、胜利都能正常结束；重复结算不会重复扣物或发奖励。
- 战斗时间只结算一次，世界与队伍状态保持一致。
- 战败是否导致死亡按模式与遭遇规则处理，战败不自动等同死亡。
- 复杂模式中实际发生主角死亡时，本局进入结束状态；突破失败路径不能触发该结果。

简单模式战败代价、NPC 战败后果、撤退成本、死亡后的物品与承诺处理，需要在相应功能实施前给出规则。测试可使用标明来源的配置，不将测试默认值当成正式玩法。

### 25.10 Milestone 7：完整修炼与突破体验

**目标：**在 M3 的共用规则上，完成凡人到筑基的玩家体验，并让 NPC 使用相同机制。

实现修炼、闭关、修为、时间成本、突破成功率展示、丹药加成、护法、失败损失与跌境结果。

突破流程建议为：检查资格 → 计算并展示成功率与可能代价 → 确认并锁定准备条件 → 推进所需时间 → 按锁定规则结算 → 原子写回角色与世界 → 生成关键事件。

成功率、消耗发生时点、护法资格和过程打断规则要在任务中说明。护法 NPC 不能同一时段出现在别处执行冲突行动；长时间闭关中 NPC 也继续演化。

**保留的产品约束：**

- 突破存在失败风险，准备可以影响成功率。
- 突破失败不致命，玩家与 NPC 均遵守。
- 失败可以损失修为，严重时可能跌境。
- 具体概率、跌落幅度、是否跨大境界、恢复规则尚待确定。
- 小境界与大境界采用何种差异化判定，按后续确认的详细境界表实现。

**验收：**

- 同等角色状态和准备条件下，玩家／NPC 得到相同计算结果。
- 展示的成功率、消耗与实际结算采用同一规则及版本。
- 强制注入成功、普通失败和严重失败分支验证结果；失败分支均不直接死亡。
- 定向测试条件边界、概率边界、修为下限与境界边界，不能只靠随机模拟碰运气。
- 闭关 30 天与对应的逐日世界推进结果一致；准备中的合法存档续跑不重复扣资源或重复突破。
- 当日其他独立事件造成死亡时有独立原因记录，不将其包装成突破失败致死。

### 25.11 Milestone 8：第一条真正的人物故事

**目标：**用一个重点 NPC 验证“这个人记得我，并因此改变行为”。

完整流程保留：相识、交谈、发现共同目标、邀请同行、秘境探索、提出战利品约定、履约或违约、不同反应、后续再遇。

该 NPC 需要一个可解释的目标、一组影响行动的性格特征、一段初始关系背景，以及可持续追踪的关键记忆。建议将重点角色写成可配置内容模板，按世界生成规则放入有效地点，避免 Seed 改变后故事入口消失。

先使用固定选项和规则对白完成这条故事。至少提供两条从同一前置存档可复现的分支：

- 履约：按约定分配物品，NPC 信任增加；下次愿意同行，或愿意接受更宽松的条件。
- 违约：玩家保留约定物品，NPC 记住具体事件；下次拒绝、要求预付或提高分配要求，具体反应由性格与规则决定。

分支必须同时改变行为和对白。若只有“谢谢你”和“我恨你”的不同台词，而下一次决策完全一致，核心体验尚未验证。

**验收：**

- 两条分支都能从相识走到离开后再相遇。
- 退出重开、加载后，NPC 仍能准确引用过去的事实与约定。
- NPC 拒绝或接受同行时，状态与关系条件能解释结果。
- 玩家未获承诺物品、NPC 提前离队、目标已完成等边界有明确结果，不出现任务卡死。
- 全流程在关闭 AI 的情况下可以完成。

### 25.12 Milestone 9：AI 自由交涉

**目标：**让自由输入能够形成有效的游戏提议，并沿用已有规则完成同一人物故事。

接入 OpenAI-compatible API，配置 Base URL、API Key、Model、Timeout、Max Tokens。具体供应方协议与支持项在实现适配器时核验；密钥放在本地设置中，避免进入版本库、游戏存档、提示词和调试日志。

第一阶段仅开放自由交涉所需的白名单意图：邀请同行、提出或修改物品分配条件、接受、拒绝或反提条件。AI 不直接发放物品、修改境界、写关系分数或决定战斗结果。

**执行流程：**

1. 游戏为当前交涉生成唯一请求 ID，保留世界修订号和参与者。
2. 提供 NPC 可知的相关事实、目标、记忆及允许的意图格式。
3. 模型返回结构化 Proposal，作为待校验候选。
4. 做格式、字段、类型、长度和枚举检查，再做规则校验。
5. 条件发生变化或模型提出新条件时，向玩家展示确切条款；未被玩家明确同意的新条件不自动执行。
6. 提交时重新检查相关状态，原子写入队伍与承诺，并生成事件。

对于“凝元草给你，其他东西平分，你陪我进入秘境”，必须先明确凝元草是立即赠送还是未来战利品；“平分”按人数、数量或价值如何分配，以及不可分物品如何处理，均应解析成可展示的确定条款。含糊时在游戏内追问。

以下只是字段结构示例，具体 ID 必须来自当前世界。请求 ID、世界修订号等可信元数据由游戏持有并校验，不以模型回传值为准。

```json
{
  "intent": "ProposePartyAgreement",
  "inviterId": "PLAYER_0001",
  "inviteeId": "NPC_0032",
  "expeditionId": "EXPEDITION_0007",
  "terms": [
    {
      "type": "FutureLootAllocation",
      "itemId": "ITEM_NINGYUAN_GRASS",
      "recipientId": "NPC_0032",
      "quantity": 1,
      "condition": "FirstMatchingDropInThisExpedition"
    }
  ],
  "unresolvedTerms": [
    "其余战利品平分的范围与算法尚未明确"
  ],
  "reason": "她正在准备筑基，希望优先获得凝元草。"
}
```

示例存在未解决条款，因此只能作为待澄清候选，不能提交。`reason` 用于解释提议，不能凭这一字段把“正在准备筑基”写成 NPC 的新事实。

**Rule Validator 至少检查：**

- 意图是否允许，ID、物品定义与条件是否有效。
- 参与者是否存活、可交涉、可组队，队伍是否有空位。
- 当前关系、目标与 NPC 意愿是否满足接受规则。
- 立即交易的物品是否持有且可支配；未来战利品承诺是否冲突、是否有明确适用范围。
- 相关世界状态是否自请求以来发生变化，条款是否已得到明确同意。
- 同一请求是否已经执行，重复或迟到响应是否应丢弃。

**验收：**

- 自由输入能够完成已有的同行与分配玩法。
- 无效 JSON、未知意图、伪造 ID、超额数量、互相冲突的承诺均不改变世界。
- 超时、断网、取消、响应重复及请求期间状态变化均有明确处理，NPC 不会因请求悬挂永久锁定。
- 关闭 AI 或调用失败后，固定选项仍能完成故事。
- 模型生成文本不能绕过规则增加物品、关系或修为。
- 已执行条款、接受者和结果进入存档；读档不会重新请求模型并改写历史。
- 单元测试使用固定响应与故障模拟；真实 API 验证作为单独集成检查，不让联网结果影响规则测试稳定性。

### 25.13 Milestone 10：第一个 Vertical Slice

**目标：**形成从创建角色到尝试筑基的可试玩版本。

玩家应能够完成以下体验：

1. 创建人物并生成世界，以凡人身份进入坊市。
2. 认识 NPC，找到修炼机会，成为炼气修士。
3. 发展关系，组成最多三人的队伍并探索秘境。
4. 完成战斗与战利品分配，看到履约或违约带来的关系后果。
5. 闭关一段时间，发现 NPC 的位置、境界、目标或关系发生合理变化。
6. 再次遇到重点 NPC，对方记得此前经历。
7. 准备并尝试筑基，看到成功或非致命失败的清楚反馈；存在可继续努力、再次尝试并成功的路径。

体验目标包括筑基成功，但单次试玩不保证突破必成，不能为了演示闭环取消失败风险。

**交付验收：**

- 提供可运行构建、运行说明、版本号、已知问题和复现用 Seed。
- 首次进入、存档、退出、继续游戏都能走完流程。
- 履约与违约分支均有可复现的存档或测试夹具。
- 无破坏存档、重复奖励、角色身份或位置冲突等阻断问题。
- 固定选项能独立完成闭环；AI 提供额外表达自由。
- 世界变化有可发现的线索，不要求玩家翻调试日志才能看见。

**试玩建议：**先邀请 3–5 人，作为小样本质性观察。记录卡住的位置、退出原因、是否理解约定，以及再次遇见 NPC 时的反应。

试玩结束后问：“你最记得谁？发生了什么？你为什么做那个选择？如果重玩会改变什么？”尽量让玩家先自由回答，再补问 AI 和具体系统。

如果玩家能自然讲出“那个 NPC 后来居然……”并解释因果，继续打磨这条核心体验。如果玩家主要记住系统术语，就优先改善人物动机、事件可见性和关系反馈。

## 二十六、开发优先级与范围管理

### 26.1 产品取舍顺序

沿用原优先级：

1. 人物是否像活人一样存在于世界中。
2. 玩家是否在经历一段修仙人生。
3. 修炼和成长是否有获得感。
4. 世界是否会自行发展。
5. AI 是否改善前述核心体验。

战斗复杂度、美术规模、宗门经营、生产系统、更多境界和地图，在核心体验通过试玩后再排序。

存档正确性、规则一致性和可复现性是交付前提，不与产品趣味性争抢名次。人物再生动，读档丢失记忆也不能验收。

### 26.2 实际开发顺序

| 顺序 | 交付阶段 | 完成后能够证明什么 |
| --- | --- | --- |
| 1 | M0 工程、时钟、随机、事件与存档骨架 | 基础设施可验证 |
| 2 | M1 角色创建、M2 世界生成 | 创建结果可保存，初始世界可复现 |
| 3 | M3A 调度、M3B 共用修炼核、M3C NPC 演化 | 世界能够长期运行 |
| 4 | M4 关系、承诺、记忆 | 人物行为开始具有可追溯的社会原因 |
| 5 | M5 最小地图 | 玩家能看到并接触世界人物 |
| 6 | M6 战斗、M7 完整修炼 | 探索和成长形成可操作循环 |
| 7 | M8 人物故事 | 一个 NPC 能留下具体印象 |
| 8 | M9 AI 自由交涉 | 自由表达能安全落入已有玩法 |
| 9 | M10 组装、试玩、修正 | 整段修仙经历值得继续扩展 |

保留原 M0–M10 编号；新增的子阶段用于明确前置依赖。每次只推动一个主要验收目标，完成后再扩内容。

### 26.3 统一完成标准

一个任务标记为完成，应同时提供：

- 可以运行或检查的具体产物。
- 对应验收步骤与结果；未执行的测试明确标记未验证。
- 与该任务风险相关的测试，重点覆盖状态一致性、存档和关键分支。
- 数据结构变化对应的版本处理，以及必要文档更新。
- 遗留问题和影响范围。

低影响的文案、布局调整可直接人工检查。涉及随机、存档、死亡、承诺、资源结算与 AI 写入的规则改动应有针对性回归。不要用大量只重复实现细节的测试代替有效验收。

### 26.4 变更规则

已经确认的产品规则保持稳定。试玩发现问题时，先记录“观察到的现象、可能原因、最小改动、影响范围和验证方式”，再决定调整。

数值调优、缺陷修复和产品规则变更分别记录。任何 Seed 结果变化都应说明是缺陷修复、算法升级还是内容变化，并更新相关版本与回归样本。

新增功能进入 Backlog，写明能改善哪项核心体验以及需要延后什么工作。仅因某个系统容易做或 AI 容易接，不自动提升其优先级。

## 二十七、启动开发前的文档与首批任务

### 27.1 三份长期基线

在仓库中建立以下文档。先写当前版本真正需要的内容，随已验收任务同步更新。

| 文档 | 必须回答的问题 | 首版内容 |
| --- | --- | --- |
| `docs/GDD.md` | 游戏承诺什么体验，哪些规则已定？ | 核心体验、玩法循环、V0.1 范围、模式、修炼、关系、美术、待定规则 |
| `docs/TDD.md` | 状态在哪里，如何正确推进和恢复？ | 分层、模型、ID、随机、时间、事件、存档、结算、AI 接口、内容扩展与测试 |
| `AGENTS.md` | Codex 怎样完成一个可审查任务？ | 修改边界、目录与依赖、任务流程、验收证据、版本及文档维护 |

本稿可作为三份文档的开发执行依据；GDD 中仍需补入前二十四节的完整产品基线。

### 27.2 TDD 的最小数据模型

| 数据／服务 | 责任与关键字段 |
| --- | --- |
| WorldState | 游戏时间、世界 Seed、版本、实体集合与待处理行动 |
| CharacterState | 玩家与 NPC 共用身份、生命、修炼、位置、物品引用等状态 |
| PlayerProfile | 姓名、外貌、模式、创建结果、法宝选择及玩家控制角色 ID |
| NpcMindState | 性格、目标、当前行动、知晓事件与记忆引用 |
| CultivationState | 境界、修为、准备、闭关或突破进度 |
| Relationship | 关系端点、有向数值、显式标签与来源事件 |
| WorldEvent / Memory | 世界事实，以及某角色对事实的知晓与保留 |
| Agreement | 当事人、明确条款、条件、期限、状态及来源 |
| Inventory / LootPool | 物品定义、数量、所有权及待分配状态 |
| PartyState | 成员、同行目标、资格与关联约定 |
| SaveEnvelope | 结构版本、规则／内容／生成器版本、随机状态及完整快照 |
| TimeService / RuleServices | 统一耗时与各领域规则，供玩家和 NPC 共用 |
| IAIProvider | 请求／取消／错误结果与候选提议，不直接引用可变世界对象 |

表格表示职责，不要求每一项都成为独立框架或大型模块。具体类数量按实现规模收敛。

### 27.3 AGENTS.md 应明确的项目规范

建议采用以下可直接落入项目规范的条目：

1. 先阅读当前 GDD、TDD 和任务验收条件，再修改相关代码；已有用户决定优先于文档中的旧建议。
2. 每个任务说明目标、前置条件、涉及模块、配置或存档影响及验收步骤。
3. Core 保持纯规则；UI、场景、网络回调不直接修改世界实体。
4. 玩家与 NPC 复用规则；确需例外时标明产品依据。
5. 核心逻辑只使用项目提供的时钟、随机源和稳定 ID。
6. 状态变更通过应用用例完成；资源、队伍、承诺等关联修改保证一次完整提交。
7. 修改存档结构或内容语义时处理版本，不静默覆盖不兼容存档。
8. 新增规则时检查对应关键不变量，特别是突破非致命与死亡后的行动取消。
9. API 凭证不入库、不入档、不入日志；AI 输出只作候选输入。
10. 每次报告写清完成内容、验证结果、未验证环境及剩余问题，不能把预期当作实测结果。
11. 按任务分支或隔离工作区开发；可独立的实现和审查可以并行，避免多方同时编辑同一核心文件。
12. 需要产品决定时，先完成已获授权且不依赖该决定的工作，再提交具体选项及其影响；普通实现细节自行判断。

### 27.4 首批可交给 Codex 的 M0 任务

**单个任务描述建议格式：**任务编号；用户可见或工程目标；前置条件；具体实现；数据与版本影响；验收步骤；交付证据；待决定问题。
