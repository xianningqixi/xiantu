## V0.1-Web 调研与设计依据

以下为上一版调研和设计说明；与当前执行包有差异的原型建议，以执行包为准。

本轮已确认的变化：游戏以 Web 页面呈现，每次主要通过文字、配图和操作进行交互。以下将这一决定落实为“图文事件驱动的修仙人生 RPG”。具体前端框架、战斗回合方式、素材数量、单幕字数和存档部署方式是本次建议，不能当成用户已逐项确认。

## 本轮设计结论

玩家打开网页，看到当前地点或事件画面、相关人物、一段描述，以及当前可执行的行动。玩家选择或自由交涉后，规则系统结算后果、推进必要的游戏时间，再呈现下一幕；人物会记得共同经历，世界也会在这些时间里演化。

“每次文字加配图”落实为每个主要交互场景都有匹配的视觉内容。同一地点内的连续对话可以复用背景和人物图，更新文字、表情与选项。是否每次操作都生成一张全新 AI 图片，用户尚未要求；本稿将其列为可选增强，不放入 V0.1 的基础依赖。

| 原方案 | Web 图文版调整 |
| --- | --- |
| Unity 工程与原生客户端 | 建议采用原生 Web 技术，浏览器打开游玩 |
| 地图行走、碰撞、靠近 NPC 按键互动 | 地点页面、可前往地点、在场人物卡和事件选项 |
| 像素行走小人与动作 | V0.1 移除这项制作任务；人物通过头像、立绘、表情呈现 |
| 场景内演出 | 场景图、人物图、短叙事、结果反馈与轻量切换 |
| 战斗场景 | 建议回合式图文战斗视图，保留三人队伍和原有行动范围 |
| JSON 文件作为直接存档介质 | 浏览器 IndexedDB 自动存档，JSON 用于导入、导出和备份 |
| EditMode／PlayMode 测试 | 类型检查、纯规则测试、存储集成测试和浏览器流程测试 |
| Mac／Parallels 的 Unity 兼容验收 | Mac 开发环境与桌面、手机浏览器验收；Parallels 可用于 Windows 浏览器补测 |
| NPC 演化、关系、记忆、修炼与 Seed | 保留，改用独立 Web 规则核承载 |
| 大模型自由交涉 | 保留候选提议与规则校验的边界 |

以前确认的古风方向继续保留。精细非像素人物立绘与新形态直接兼容；古风像素场景也可作为背景图使用。若要将背景进一步统一成非像素古风插画，应通过一组样例再决定，不能因改为 Web 就默认推翻全部美术风格。

## 一、调研：哪些形式值得借鉴

调研使用官方游戏介绍、开发者设计文章和工具官方文档。案例说明存在可借鉴的形式；本项目是否好玩、具体性能和成本仍需原型验证。历史设计文章用于叙事方法参考，不用于判断今天的商业表现。

| 参考对象 | 一手资料能确认的事实 | 本项目采用的设计启发 |
| --- | --- | --- |
| Fallen London | 官方定位包含互动小说、文字冒险和 RPG，支持桌面及手机浏览器，采用响应式界面。[官方介绍](https://www.failbettergames.com/games/fallen-london) | 地点、人物、资源与选择可以通过网页承载；玩家不需要操纵小人才能探索世界 |
| Failbetter 的 Storylet 设计 | 短叙事单元由状态条件开放，也可用进度连接；拆分叙事单元有助于控制巨大分支树的扩张。[结构 Part 2](https://www.failbettergames.com/news/echo-bazaar-narrative-structures-part-two)、[Part 3](https://www.failbettergames.com/news/echo-bazaar-narrative-structures-part-three) | 建立由地点、人物状态、关系、承诺和历史触发的事件模板库；重点人物故事由多个事件连接 |
| Ink / Inky | 官方工具支持叙事创作与 Web 导出；Web 模板可通过标签插入图片，文本和图像呈现可以分工。[Web 教程](https://www.inklestudios.com/ink/web-tutorial/) | 可以借鉴选项、分支汇合和图像标签；是否采用 Ink 作为内容工具，等事件模板原型完成后再评估 |
| ChoiceScript | 官方入门展示以变量记录选择，并影响之后的情节或结果。[官方入门](https://www.choiceofgames.com/make-your-own-games/choicescript-intro/) | 把选择造成的真实状态变化与之后的叙述对应起来，控制长篇分支的重复劳动 |
| AI Dungeon | 官方支持在冒险中请求配图，生成需要等待，通常涉及 Credits；其 Story Cards 是按相关性进入上下文的设定笔记。[配图说明](https://help.aidungeon.com/faq/how-do-i-create-pictures-in-ai-dungeon)、[Story Cards 说明](https://help.aidungeon.com/faq/story-cards) | 自由输入和配图具有可参考的交互方式；本项目仍用结构化世界、事件和 NPC 知情记录管理事实，再向模型提供需要的上下文 |

**建议采用的组合：**状态驱动的短事件组织、人物立绘和场景插画呈现、固定行动选项、可选自由交涉。世界规则、人物记忆与资源结算独立于叙事文本。

不照搬案例中的商业机制。现实时间体力恢复、付费抽事件、联网持续世界等，均不因采用相似界面而进入本项目需求。

## 二、玩家每次如何交互

### 2.1 一个主要交互场景的结构

主界面围绕“我在哪里、遇见了谁、发生什么、现在能做什么”组织。

| 区域 | 内容与规则 |
| --- | --- |
| 简要状态 | 游戏日期、地点、境界、重要伤势或资源；更详细属性进入人物页 |
| 画面 | 当前场景图；相关 NPC 出现时显示其固定立绘或头像；重要事件可换专属插图 |
| 叙事 | 本次发生的事、NPC 的话和可感知的线索；普通事件建议先以 80–180 个汉字测试阅读节奏，重点剧情按需要展开 |
| 行动 | 通常 2–4 个当前有效选项，写明已知消耗、耗时及必要条件；数量与字数均为原型建议 |
| 自由交涉 | 在有交涉对象的场景中提供“另提条件”；玩家可继续使用固定按钮 |
| 结果 | 一段简短后果描述，配合物品、时间、伤势等重要变化；关系变化优先表达原因，精确数值展示程度待定 |
| 历程 | 已发生事件可回看，已执行选项不可再次提交；旧画面不被当成当前状态 |

每次浏览档案、看历史或读一段对白，不必新开事件、换图或推进一天。只有具有游戏后果的行动才提交命令；是否耗时由行动定义决定。普通寒暄不因反复点击就无限增加关系。

建议把“当前一幕”和“历史记录”分开：默认聚焦当前画面、文字与选项；过去内容进入可展开历程，避免长时间游玩后只能在很长的对话流末尾寻找按钮。

### 2.2 桌面与手机布局

桌面可采用主叙事区配合较窄的状态／人物侧栏；手机采用单列，从场景图、人物、正文顺序到操作。人物档案、背包和历程通过明确入口打开。

正文保持可选取的 HTML 文本，选项使用真实按钮，输入使用原生文本框。图片不能承载唯一的规则说明；提供替代文字。页面支持键盘和触摸，重要信息不依赖鼠标悬停。

图片预留尺寸，加载后不挤走正在点击的选项。长文可展开；轻量过渡可关闭；自动战斗可跳过逐条动画。字体、对比度和按钮间距以手机实测为准，不追求把全部属性挤进一屏。

### 2.3 一段可直接制作的交互样例

以下角色、地点、台词和数值仅为原型占位，不新增正式人物设定。

**场景：青石坊市，初识林晚。**

画面：坊市背景、林晚固定立绘。

> 药摊前的女修反复掂量着钱袋，最终把凝元草放回木匣。摊主转身招呼旁人，她却仍盯着草叶。见你停步，她收起钱袋：“道友也是来寻药的？”

可选行动：询问她需要什么；打听附近秘境；结束交谈。符合交涉条件时可“另提条件”。

玩家得知她准备筑基后，提出本次秘境第一株凝元草归她的同行约定。界面展示明确条款、参与者和当前未解决条件。只有双方接受且条件完整，才建立队伍与承诺。

**数日后，履约分支再次相遇。**

画面：沿用坊市背景与同一人物，切换适当表情。

> 林晚收起药谱，主动替你挪开身旁的木凳：“上回凝元草的事，我记着。这次若再进秘境，叫上我便是。”

出现“邀请同行”等符合当前状态的选项；NPC 的信任及接受条件有实际变化。

**另一局中，违约后再次相遇。**

> 她看了一眼你的行囊，没有让座：“上次说好的凝元草，道友也是这样答应的。若还想同行，先把分法写清楚。”

可能出现解释、补偿、提出更明确条件或离开的选项。后果由事实、性格和规则决定，不能仅换一段台词而保持所有行为不变。

### 2.4 探索、修炼、战斗分别怎样呈现

| 玩法 | 图文交互设计 |
| --- | --- |
| 地点探索 | 当前地点背景、在场人物、可访问设施、可前往节点；旅行选择显示耗时与已知风险 |
| 人物交往 | 固定人物图、对白、关系原因、共同经历、承诺与邀请选项 |
| 日常修炼 | 选择修炼方式和时长，提交后展示结果与期间重要世界动态 |
| 闭关 | 选择天数和准备，模拟过程显示进度；完成后给修为结果、熟人近况和需要关注的约定 |
| 突破 | 展示条件、成功率、消耗和可能代价；确认后结算，成功或失败有对应图文反馈 |
| 秘境 | 节点式探索：入口、岔路、遭遇、资源、出口；已知路线和撤离条件清楚可见 |
| 战斗 | 建议独立回合视图：敌我人物卡、状态、主角行动按钮、NPC 自动行动、精简战报和可展开细节 |
| 世界变化 | 优先展示玩家经历、熟人变化和可获知传闻，普通 NPC 日常变化在后台结算 |

三人队伍、主角手动、NPC 自动、自动战斗、普攻、四技能槽、防御、丹药、撤退、胜负和掉落继续保留。回合制是为新交互形式提出的建议，具体先后手、技能与战败规则在 M6 前确认。

## 三、事件、配图与内容制作

### 3.1 事件模板驱动，状态决定资格

事件模板定义触发条件、参与者筛选、文字模板、图片引用、可选行动、后果入口、重复限制和故事进度。运行时先查当前世界，再选出合适事件，最后生成页面。

候选事件先过滤，再按优先级、近期重复和冷却排序，确有需要时使用独立叙事随机流抽取。抽取结果进入会话状态，刷新不能不断重抽事件；文字修饰或图片选择不消耗修炼、战斗的随机源。

同一事件中的剧情进度、承诺履行状态和人物信任分别保存，避免用一个好感数字承担所有含义。这也是对 Failbetter 关于状态变量语义混用问题的工程借鉴。[叙事工程复盘](https://www.failbettergames.com/news/dont-poke-that-narrative-engineering-principles-part-1)

内容分为三类：

- 常规行动：修炼、前往地点、看背包等稳定可用入口。
- 通用事件：交易、求助、邀约等模板，绑定符合条件的角色与地点。
- 重点人物事件：一个 NPC 的精细故事节点，引用真实关系、目标和共同经历。

V0.1 建议先制作约 12–20 个通用事件模板、一个 6–10 节点的重点人物故事，用于验证事件重复率与分支可玩性。数量是初始内容预算，可根据实际体验调整。

### 3.2 事实结算与叙事呈现的接口

建议使用以下职责分离，而不是让文本直接修改世界：

| 数据 | 作用 |
| --- | --- |
| StoryletDefinition | 静态事件模板：条件、参与者规则、文字、图像和行动定义 |
| InteractionSession | 当前事件实例、参与者、章节进度、已展示选项与所依据的世界修订号 |
| GameCommand | 玩家确认的行动及参数、唯一命令 ID、前置修订号 |
| CommandResult / WorldEvent | 规则结算后的权威变化与事实 |
| SceneViewModel | 向界面提供的文字、画面、有效选项、已知消耗和结果摘要 |
| JournalEntry | 玩家已经看到的关键叙事与其事实引用；回看不触发执行 |

画面和文字必须与同一份已提交状态对应。物品未获得时不描述为已收入囊中；NPC 未到场时不显示其正在当面说话。远程传讯如后续引入，应有独立通信规则与视觉标识。

点击选项时重新验证资格，不能因为按钮此前出现过就认定仍有效。浏览器返回、重复点击、网络迟到响应都不能重复扣资源或推进时间。

### 3.3 配图的默认方案与升级路径

| 方案 | 本项目用途 | 影响 |
| --- | --- | --- |
| 预制场景图＋固定人物图＋表情 | V0.1 默认，每个主要事件提供匹配画面 | 角色形象稳定，读取快，成本可以预先控制 |
| 关键事件专属插图 | 相救、违约、重逢、突破等少量高价值节点 | 增强记忆点；先按内容预算制作 |
| 游玩中实时 AI 生图 | 后续可选，或玩家主动请求“生成这一幕” | 需要等待与费用控制，还需验证角色一致性、错误画面和失败回退 |

使用 AI 在开发阶段批量制作预制素材，与玩家每次操作时调用生图接口，是两种不同方案。默认可以用前者提高制作效率，正式素材需统一检查风格与人物身份。

建议首批资源：4–6 张场景图；重点 NPC 一套固定立绘和少量表情；普通 NPC 使用与身份绑定的头像或合法部件组合；3–5 张关键事件插图及少量物品、状态图标。先做适配模板再扩数量，不要求为 40 名 NPC 一开始各画全套立绘。

普通 NPC 也要保持可识别性，不能刷新就换脸。资源不足时使用稳定的头像框、衣色和人物文字描述区分，避免把同一完整立绘当成多个重点人物。

原型建议以场景横图和人物竖图为基础，手机用适配裁切；重点面部和关键道具保留安全区域。资源清单记录 `assetId`、角色绑定、风格版本、用途、尺寸、替代文字与来源。存档保存稳定 ID，不把大幅图片以 Base64 反复塞入每个事件快照。

实时生成图片不纳入 Seed 复现保证。若未来启用，需要保存最终选中的资源及稳定引用；生成失败继续使用有效预制画面。图像可以异步完成，物品、时间与关系不得因图片请求成功或失败而重新结算。

## 四、Web 技术设计建议

### 4.1 V0.1 默认：单人、本地优先

建议采用 React + TypeScript + Vite，规则核与界面分离，长模拟使用 Web Worker，存档使用 IndexedDB。React 官方提供从 Vite 等构建工具起步的路径，Vite 提供 React / TypeScript 模板；下面的领域分层是本项目建议。[React 文档](https://react.dev/learn/build-a-react-app-from-scratch)、[Vite 文档](https://vite.dev/guide/)

| 模块 | 职责 |
| --- | --- |
| `src/core/` | 纯 TypeScript 模型、时钟、随机、修炼、战斗、关系与事件规则；不依赖 React、DOM、浏览器存储或 HTTP |
| `src/application/` | 创建角色、行动、推进时间、校验与结果编排，定义持久化和 AI 等端口 |
| `src/infrastructure/` | IndexedDB、导入导出、日志、AI 代理客户端等适配 |
| `src/worker/` | 规则运行宿主、串行命令队列、模拟进度和消息协议，复用 core 与 application |
| `src/ui/` | 图文场景、人物档案、战斗、设置和状态展示，只提交请求及显示结果 |
| `src/content/` | 经过结构校验的事件、物品、境界和内容清单；先使用简单 JSON／类型化数据 |
| `public/assets/` | 版本化图片等静态资源 |
| `tests/` | 规则、存储、内容校验和浏览器流程测试 |

应用启动入口装配这些模块。核心逻辑优先保持简单，不为尚未需要的复杂依赖引入大型框架。Ink 可以在重点人物文本变复杂后作为内容适配器引入，V0.1 不同时维护两套剧情状态。

### 4.2 世界权威与运行时机

V0.1 每个存档是一局独立的单人世界，浏览器内规则宿主负责其权威状态；服务端 AI 代理只返回候选内容，不拥有这局世界。玩家与 NPC 共用修炼、突破、战斗、物品和关系规则。

世界随确认的游戏行动推进。读面板、浏览历史、图片加载、AI 等待和退出网页期间不推进游戏日。所谓“世界自行发展”，首先指玩家旅行、修炼、闭关时，NPC 同步演化。现实时间挂机另立需求。

Web Worker 能在主线程之外执行任务，通过消息通信，适合将长模拟从 UI 主线程移开；这不等于关掉网页后仍有后台游戏服务器。[MDN：Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API)

建议逐日确定性结算，分批汇报进度。闭关保存为带 longActionId 的长行动，每个完整检查点作为独立分段命令提交；该段的世界状态、随机状态、已扣资源、剩余天数和去重记录同事务保存。UI 区分“正在计算”和“已保存”，重新打开只从最后已提交检查点续跑。

暂停计算只是停止处理后续天数，角色仍处于闭关中；实际提前出关是另一条游戏命令，按确认的中断规则处理。两者都不能退回已结算天数或重复扣准备资源，是否允许提前出关及其代价在 M7 明确。

### 4.3 命令、自动保存与重复执行

每条命令具有唯一 ID、存档 ID 和期望世界修订号。规则核先计算候选结果，经验证后，把新状态、随机状态、事件、会话进度和命令执行记录写入同一 IndexedDB 读写事务；事务成功后才确认行动完成并向 UI 发布结果。

IndexedDB 是支持事务的异步结构化存储；应用必须区分单项写入成功与整笔事务完成，后者才是本次保存成功信号。[MDN：IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)、[IDBTransaction](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)

存储失败时保留上一次完整状态，候选结果不得被当成已完成；明确显示保存失败及可用恢复操作。同一事务还要读取并检查当前修订号，防止两个标签页用旧状态覆盖对方。建议同一存档只允许一个活动写入页面，其他页面提示重新加载；存储层修订检查仍是最后保障。

重复命令返回已有结果；过期选项、已执行约定和迟到 AI 响应需拒绝或刷新。页面刷新、回退和重新挂载组件都不是新行动，不能触发新的世界结算。不能把可靠保存只寄托在关闭页面事件上。

### 4.4 存档内容、版本与迁移

存档包含角色创建结果、模式、世界状态、NPC 行动、游戏时间、所有随机源状态、物品、队伍、关系、关键记忆、承诺、故事进度、当前交互实例和命令去重信息。

分别记录数据库结构版本、存档格式版本、生成器版本、规则版本、内容版本与素材版本。数据库升级与游戏数据迁移分开设计；迁移在副本上验证，失败保留可读版本，不静默重置世界。旧页面收到 versionchange 后停止接受新命令并关闭旧连接；升级遇到 blocked 时提示关闭或刷新旧页，不能静默挂起。[MDN：使用 IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)

首次运行提供本地存档说明，设置页提供导出／导入 JSON。浏览器数据默认不自动跨设备、浏览器或域名同步，且可能被清理；持久存储申请也不能替代备份。[MDN：存储配额与清理](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

JSON 导入先校验格式、版本、引用、数值边界和体积，成功后创建或明确替换目标存档。云备份／跨设备同步可后续加入，需要账户、版本冲突及恢复规则；不属于“做成网页”自动获得的能力。

复杂模式的真死亡写入本局终止状态。该规则在正常玩法中生效；本地优先版本不承诺防用户修改存档或恢复旧备份。可信排名、交易或共享世界若以后出现，需要另评估服务端权威。

### 4.5 确定性与长模拟

固定世界 Seed、生成器版本、规则版本、内容版本和初始配置，才能要求初始世界一致。玩家资料单独保存，资质重掷使用独立随机流。后续模拟还需相同的命令序列、执行顺序与随机状态。

使用项目指定且可序列化的伪随机算法，不用 `Math.random()` 承担可控 Seed；该函数的初始种子无法由调用者选择或重置。[MDN：Math.random](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/random)

世界生成、创建重掷、世界演化、战斗和叙事抽取使用明确分离的随机源。已展示的场景保存稳定实例，外观动画与文案修饰不改变规则随机。核心数值优先采用整数／固定精度方案，实体按稳定 ID 顺序处理。

验收比较规范化逻辑摘要，排除现实时间、浏览器窗口大小和资源下载顺序。AI 临时文案和实时生图不要求重新调用仍相同；关键已展示文本、已接受提议和最终资源引用应保存，回看历史不重新创造事实。

100 NPC × 3650 天保留为长期正确性与规模验证，记录设备、浏览器、耗时、存档体积及内存观察，不先写未经实测的秒数保证。

### 4.6 AI、离线与部署边界

M9 接入个人部署的 AI 代理服务。共享 API Key、上游 Base URL 和可用模型由服务端配置；网页只调用自己的受控服务。前端公开构建变量不存密钥，`VITE_*` 会暴露给客户端代码。[Vite：环境变量](https://vite.dev/guide/env-and-mode)

服务端限定供应方、模型、超时和请求规模；对他人开放前设置相应访问控制和用量限制。错误反馈可理解，日志脱敏。公开部署不接受任意上游地址作为通用转发服务。

第一次上线验证仍以固定选项可独立游玩为标准。自由交涉的模型候选必须经过同一规则校验；这一步校验对本地游戏一致性负责，不声称阻止玩家自行修改本地游戏。

区分两项能力：关闭 AI 后规则与固定选项仍可用；断网后重新打开整个网站仍可玩。后者需要 Service Worker 缓存应用、规则内容和必要图片，生产环境采用 HTTPS，安排在最终切片集成中验证。[MDN：Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)

已成功缓存且未被清理的素材可离线使用；曾经下载过图片不等于下次一定可离线读取。首次离线重开前需要完成应用、规则和必要素材的缓存，并显示准备是否完成；未缓存的新图不阻断操作。更新缓存必须按内容包版本切换，不能把新规则配上旧内容或让旧页面写坏新结构存档。

### 4.7 测试工具

建议用 Vitest 验证规则与内容，用浏览器集成测试验证真实 IndexedDB，用 Playwright 覆盖关键流程。类型检查单独运行；Vite 对 TypeScript 的转译不代替类型检查。[Vitest](https://vitest.dev/guide/)、[Vite TypeScript 说明](https://vite.dev/guide/features)

Playwright 可覆盖 Chromium、Firefox 和 WebKit，并进行移动设备参数模拟；关键移动流程仍需真实 iPhone Safari 实测。[Playwright 浏览器](https://playwright.dev/docs/browsers)、[设备模拟](https://playwright.dev/docs/emulation)

## 二十五、第一批 Codex 开发任务：Web 版

### 25.1 V0.1 范围

初始世界约 40 名 NPC；一个坊市入口、一处最小秘境和必要的修炼地点；凡人、炼气、筑基三个阶段；最多三人队伍；一个重点 NPC 的履约与违约故事；固定选项完整可玩，AI 自由交涉作为增强。

保留姓名、男女选择、外貌配置、资质无限重掷、三件专属法宝三选一、简单／复杂模式、好感／信任／吸引、朋友／挚友／敌对／仇人／恋人／道侣／夫妻等关系的产品方向。关系建立细则、法宝效果和未确认数值仍需按相应任务补齐。

已经明确的突破约束继续有效：突破存在失败风险，准备可以改善成功率；失败不致命，可损失修为，严重时可能跌境。幅度、概率、是否跨大境界及恢复规则尚待确认。复杂模式在其他场景真正死亡后本局结束。

### 25.2 Milestone 0：Web 工程与最小图文交互壳

**目标：**先让浏览器能够展示和操作一小段图文事件，同时建立基础工程边界。

实现内容：

- 创建 React + TypeScript + Vite 工程，初始化 Git、锁文件、格式检查、类型检查和测试入口；锁定实际依赖与运行环境版本。
- 建立 core、application、infrastructure、worker、ui、content 和 assets 的职责边界。
- 做三个占位场景：坊市初识、约定分配、再次相遇，先用固定测试数据切换画面和选项，明确它们是界面夹具。
- 图片和文字布局支持桌面与手机；图片缺失有替代呈现，选项仍能操作。
- 建立最小时钟、稳定 ID、可序列化随机接口、结构化事件与统一日志。
- 完成 Worker 消息往返，以及最小状态的 IndexedDB 原子保存、读取和 JSON 导出／导入验证。

**验收：**

- 干净检出后按 README 启动，类型检查、构建和相关测试通过。
- 桌面与手机宽度能完成三幕操作，无文字重叠、按钮遮挡或图片加载引起的误点。
- 刷新恢复最小测试状态，重复命令不会多执行一次。
- 主线程不直接运行长模拟；测试确认 Worker 消息契约有效。
- 此阶段仅证明工程与呈现，不以占位剧情冒充完成的世界或关系系统。

### 25.3 Milestone 1：角色创建与浏览器恢复

实现 PlayerProfile、姓名、男女选择、固定外貌配置、资质生成和无限重掷、三件法宝三选一、模式选择以及创建后的自动保存。外貌图与配置绑定，重开不会换脸。

尚未提供具体法宝名称与效果时，使用显式标明的测试定义验证选择流程；正式内容验收前补齐。重复提交创建请求不能重复发放法宝。

**验收：**

- 创建、刷新、关闭再打开同源页面，核心角色数据保持一致。
- JSON 导出后导入新测试环境，数据一致；非法输入不会破坏已有存档。
- 资质重掷不消耗世界生成随机流，用独立随机接口测试验证。
- M2 完成后补做“重掷前后初始世界一致”的集成验收。
- 当前创建模式进入存档，后续结算能够读取相应规则配置。

### 25.4 Milestone 2：确定性世界生成

实现区域、地点节点及连接、势力、约 40 名 NPC、初始关系和游戏日期；使用调试列表查看生成结果。

NPC 至少包含稳定 ID、姓名、性别、出生游戏日／年龄、外貌定义、性格、资质、境界、修为、势力、当前位置或唯一旅途状态、目标、当前行动及初始关系。

生成顺序固定：区域和地点、势力、人物、社会关系，最后统一检查。关系必须指向存在的人物；师徒合理性结合拜师时间与资格，不能只按谁更年长判定。

**验收：**

- 同版本与配置、Seed 12345，多次生成的规范化核心状态摘要相同。
- 固定另一 Seed 出现初始差异；资质重掷不改变同 Seed 的 NPC 与地点。
- 每个存活人物恰有一个有效位置状态；旅途中不同时占据两个地点。
- 势力、地点、人物与关系引用有效；世界存读档后摘要一致。
- 人物图由稳定绑定决定，不以每次页面渲染重新随机选择。

### 25.5 Milestone 3：时间、共用修炼核与 NPC 演化

拆成 M3A 调度、M3B 修炼最小核、M3C NPC 规则行为。

M3A 采用明确的日级结算阶段：到期与生存状态检查、抵达与资格检查、行动提案、共享资源裁决、行动／遭遇结算、关系后果、不变量检查、检查点提交。阶段内使用稳定顺序，死亡后立即取消后续行动。

M3B 提前实现玩家与 NPC 共用的修为、境界条件、突破判定及失败结果。用标明版本的测试配置验证，M7 再补完整准备与操作体验。

M3C 使用有限规则或优先级选择修炼、移动、交往、冲突等行动，记录原因和关键事实。NPC 冲突先通过最小共用遭遇结果接口结算，M6 接入完整战斗规则。寿命和冲突等死亡原因单独定义，突破失败始终不致命。

长闭关采用父行动 ID、确定的检查点编号、剩余天数及准备资源状态；各完整检查点单独原子提交。暂停、刷新后恢复相同父行动，不重复执行检查点。处理日数和耗时均不使用浏览器定时器触发次数计算。

**验收：**

- 固定多 Seed 回归集，100 NPC 模拟 3650 天；在中间结算点持续检查不变量。
- 死者不活动，历史身份仍可引用；地点唯一；离宗后不能继续执行已失去资格的任务。
- 数量、修为和引用合法，资源争用有明确裁决。
- 连续 100 天与 40 天后保存加载再运行 60 天一致；推进 30 天与逐日推进 30 次一致。
- Worker 长模拟时仍能看到进度并操作允许的界面；中断后恢复最后完整检查点。
- 失败报告 Seed、规则版本、游戏日、相关实体与最近事件。
- 记录实际耗时和存档增长，性能优化针对测得的瓶颈进行。

### 25.6 Milestone 4：关系、承诺与记忆

好感、信任、吸引建议按 A 对 B 与 B 对 A 分别建模；关系标签和建立条件单独定义。朋友、敌对与恋人等标签是否互斥、道侣和夫妻的关系如何转换，按明确状态规则实现。

世界事件记录事实；NPC 记忆记录其经历或获知的内容，包括来源。共同经历引用双方确实参与或知情的事实。回看历史、反复打开人物页不增加关系。

承诺记录当事人、对象、数量、履行条件、期限或触发范围、来源事件和状态。建议区分待履行、履行、违约、取消与客观无法履行；“本次掉落的第一株凝元草归你”在没有掉落时不自动算违约。

**验收：**

- 关系变化能追溯到具体事件，并影响未来邀请、交易或交涉条件。
- 同一事件重复处理不重复改变关系。
- 不知情角色不会自动知道玩家的秘密行为。
- 记忆、承诺与关系存读档一致；死者记录不会造成历史悬空。
- 亲密关系不能仅由某一数值越线自动成立，须满足已定义的建立规则。

### 25.7 Milestone 5：图文事件引擎、地点与探索

这是原“最小地图与行走”里程碑的正式替代。将 M0 的界面壳接到真实世界、关系与内容数据上。

实现：地点页面、在场人物、可前往节点、场景图与人物图、事件筛选、条件选项、结果反馈、历史回看，以及一个可重复进入且有合理变化的测试坊市。

事件实例保存参与者、当前节点、已显示内容和世界修订号。前往地点使用旅行规则推进时间；查看人物档案不推进时间；事件可包含多轮无耗时对白和有耗时行动。

补充内容检查：参与者筛选有解、合法退出入口、条件和后果引用有效、重要事件可达、已完成事件不会无故重开。允许离开或拒绝的事件应有相应按钮；真正受约束的遭遇说明其原因。

**验收：**

- 看到的人物确实在场且可互动；远程事件按另行定义的通信条件处理。
- 条件不满足的选项隐藏或解释锁定原因，不出现可点击但无响应的假选项。
- 每幕配图与地点、人物和事实一致，资源缺失不阻断操作。
- 同一事件刷新后保持当前节点和已确定随机结果；旧选项重复提交无效。
- 常规行动、重点事件和世界摘要层次清楚，不向玩家倾倒 40 名 NPC 的逐日日志。

### 25.8 Milestone 6：图文战斗与战利品结算

建议采用回合式交互，具体先后手和每回合动作数在任务开始前确认。保留最多三人、主角手动、NPC 自动和自动战斗，先做少量技能与敌人。

战斗页面提供敌我人物卡、生命与重要状态、普攻、四技能槽、防御、丹药、撤退；每回合展示主要变化，细战报可展开。主角手动和自动模式共用合法行动集合，NPC 不通过大模型逐回合决定操作。

实现最小背包、消耗品、待分配战利品池和承诺对接。战斗耗时、胜负、伤势、死亡、掉落与关系事件一并通过规则写回。

建议 V0.1 在完整回合边界自动保存 BattleState，包含行动轮次、随机状态、队伍、消耗和待结算结果。刷新后恢复最后完整回合；动画播放位置不属于权威状态。若暂不做回合内保存，则只能恢复已声明的战前检查点，不能同时声称刷新后原样继续。

**验收：**

- 角色资格、队伍人数、技能与物品消耗正确；死亡角色停止行动。
- 自动与手动使用相同规则；不因跳过动画或连点而多行动。
- 胜利、撤退和失败均能结束并只结算一次；承诺物品先进入正确的分配流程。
- 回合边界刷新不重掷结果、不重复吃药或发放掉落。
- 复杂模式实际主角死亡后本局结束；战败与死亡的关系按模式和遭遇规则定义。
- 时间结算只有一个入口，战斗视图与世界模拟不重复扣天数。

### 25.9 Milestone 7：完整修炼与突破图文体验

在 M3 共用修炼核上补修炼方式、闭关时长、丹药、护法、准备条件、成功率和完整结果页。

突破顺序：检查资格，显示成功率和代价，玩家确认，锁定或按规则处理准备条件，推进时间，结算成功或失败，原子保存，再显示反馈。准备消耗时点、护法资格、打断规则与成功率变化时机必须明确。

护法 NPC 在占用期间不能同时执行冲突行动。闭关总结只展示修为结果、相关熟人变化、可知世界动态与需要处理的约定；未知变化继续留在世界中，等待玩家发现。

**验收：**

- 同等条件下玩家／NPC 使用相同规则。
- 展示的成功率与实际判定来自同一配置。
- 定向覆盖成功、普通失败、严重失败、修为下限和境界边界；突破失败均不直接死亡。
- 跌境幅度、跨境界与恢复规则采用明确标注的配置，未确认数值不伪装定案。
- 刷新或中断后按检查点续跑，不重复扣准备物品、延长护法占用或重做突破。
- 若其他独立事件造成死亡，单独记录原因，不将其归为突破失败致死。

### 25.10 Milestone 8：第一条人物故事

只精做一个重点 NPC：相识、了解目标、共同探索意愿、同行、战利品约定、秘境、战斗、履约／违约、离开后再遇。

重点角色采用内容模板进入有效世界位置，故事事件引用其真实目标与状态。需要延后或替代节点时有规则，NPC 提前离开、受伤或目标已完成不会令主流程无响应。

**验收：**

- 从同一前置存档分别走通履约与违约，后续行为与对白都有差异。
- 同一 NPC 在不同事件、不同设备导入存档后保持身份、外貌与已发生历史一致。
- 退出再加载，NPC 仍准确引用过去发生且其知情的事件。
- 没有承诺物品掉落、NPC 离队和目标变化都有明确结果。
- 固定选项能够完成整个故事。
- 找少量试玩者验证：他们能说清“这个人为什么这样对我”，并注意到世界中的变化。

### 25.11 Milestone 9：受规则约束的 AI 自由交涉

保持第一阶段只有“自由交涉”。使用已有事件提供的对象和上下文，开放邀请同行、修改分配条款、接受、拒绝和反提条件等有限意图。

客户端保留请求 ID、世界修订号和当前会话；代理调用模型返回候选 Proposal。玩家的新承诺需要明确同意；NPC 是否接受由真实目标、关系、资源和资格规则决定。

例如“凝元草给你，其他东西平分，你陪我进入秘境”，必须澄清立即赠送或未来掉落承诺、数量、适用秘境、参与人数、其他战利品如何分配，以及不可分物品的处理。未解决条款留在协商状态，不能直接组队或转移物品。

建议 Proposal 包含意图、目标人物、适用事件／探索、明确条款、未解决条款和理由。可信的请求标识与状态版本由宿主管理；理由仅解释候选，不成为新事实。

校验包含：格式与白名单、有效 ID、角色存活与在场条件、队伍容量、NPC 意愿、物品支配权、承诺冲突、同意状态、当前世界版本及重复执行记录。通过后统一写入状态、事实与记忆。

**验收：**

- 固定按钮与合法自由交涉可形成相同语义的结果，底层后果一致。
- 无效 JSON、伪造物品、超额数量、未达成的新条款和过期回应不改变世界。
- 超时、断网、取消、迟到和重复响应不造成重复扣物或推进时间。
- AI 不可直接修改修为、境界、关系数值和掉落。
- 模型失败时固定选项继续可用；关键已执行条款与叙事入档，加载后不重新请求模型改写历史。
- 单元测试采用固定响应；真实供应方验证作为单独集成检查，记录调用次数与等待时间。

V0.1 默认文本由事件模板和规则生成。AI 叙述润色、普遍闲聊、实时事件生图可以后续逐项实验，不能与“接入自由交涉”一起默认全部实现。

### 25.12 Milestone 10：第一个 Web Vertical Slice

完整体验：创建角色，生成世界，以凡人身份进入坊市，结识 NPC，找到修炼机会，成为炼气修士，三人探索，战斗与分配，人物关系变化，闭关和世界同步演化，再遇熟人，准备并尝试筑基。

单次试玩保留突破失败风险，同时存在继续准备、再次尝试并成功的路径。阶段目标是“修仙人生和人物因果能通过图文成立”。

**交付：**可运行 Web 构建、版本与运行说明、关键 Seed／测试存档、已知问题、主要素材清单以及实际验证结果。发布环境与访问范围在真正部署任务中落实。

**验收：**

- 桌面主要浏览器和真实 iPhone Safari 走通关键流程；移动端输入、图片裁切和按钮可用。
- 页面刷新、关闭再打开、导出导入保持世界、人物、事件和战斗检查点一致。
- 履约／违约均可复现；无存档损坏、重复掉落、死者行动和位置冲突等阻断问题。
- 图片请求失败、AI 故障都不阻断固定选项闭环。
- 若交付完整离线体验，已首次加载的版本可断网重开，核心页面、内容和必要素材可用；缓存更新不混用内容版本。
- 长闭关不会让页面失去基本响应；给出目标设备上的实际耗时与资源记录。

首轮建议 3–5 人，以质性反馈为主。记录阅读是否疲劳、选项是否清楚、配图是否帮助识别人和地点、结果是否值得期待、重逢是否有记忆点；不把小样本当成市场结论。

## 二十六、开发优先级与范围管理

### 26.1 保留的核心优先级

1. 人物是否像活人一样存在于世界中。
2. 玩家是否在经历一段修仙人生。
3. 修炼和成长是否有获得感。
4. 世界是否会自行发展。
5. AI 是否改善上述体验。

在新形式下，阅读节奏、选项质量、人物识别和后果反馈是实现这些目标的主要手段。增加长篇文字、插图数量或模型调用量本身不代表体验进步。

存档正确、规则一致和事实可追溯是交付前提。事件内容、世界规则和画面必须对应，不允许用好看的图遮住未发生的事实。

### 26.2 实际顺序与阶段关口

| 阶段 | 完成后要回答的问题 |
| --- | --- |
| M0 图文壳与工程 | 手机上阅读、看图和选择是否顺畅？工程能否可靠保存最小状态？ |
| M1–M2 角色与世界 | 创建结果能恢复，初始世界能复现吗？ |
| M3 长模拟 | 时间推进后世界能保持一致吗？ |
| M4–M5 关系与事件引擎 | 事件是否引用真实人物与过去，能否形成有意义的选项？ |
| M6–M7 战斗与成长 | 探索和修炼是否有可操作、有后果的循环？ |
| M8 人物故事 | 玩家是否记住具体 NPC 及与其发生的事？ |
| M9 自由交涉 | 自由表达是否带来额外价值，并可靠落入规则？ |
| M10 试玩切片 | 图文形式能否支撑完整的修仙经历？ |

早期图文壳用于验证交互，世界和事件系统完成后替换测试数据。若单幕已经太长或选择难以理解，先调整交互密度，不靠更长的剧情补救。

### 26.3 本版先控制的规模

优先完成一个坊市、一处秘境、一个重点人物故事。金丹、宗门经营、复杂生产、多人联机、实时后台世界、完整 Mod 编辑器、自动云同步和每回合实时生图进入后续 Backlog，按试玩价值排序。

Mod 在本版保留稳定内容 ID、结构化内容包和版本信息；先支持开发者替换合法数据，不提供任意脚本执行。美术可以分批扩充，素材来源与版本要可追踪。

### 26.4 统一完成标准与变更规则

任务交付包含可检查产物、验收步骤与实际结果、必要版本处理、剩余问题和影响范围。类型检查、规则测试、真实浏览器测试各自报告，不能用“构建成功”覆盖全部验收。

对随机、存档、死亡、承诺、战斗结算与 AI 写入做针对性测试；低影响文案和样式修改可人工检查。已有验证足够时不额外扩大测试工程。

试玩变更先记录现象、原因假设、最小调整及验证方式。数值调整、缺陷修复和规则改变分别记录；改变 Seed 结果时同步更新生成器／内容／规则版本及回归样本。

### 27.2 AGENTS.md 的核心约束

1. 先阅读 GDD、TDD 与当前 Task；用户的新决定优先于旧稿。
2. core 不依赖 React、DOM、HTTP 或存储，玩家和 NPC 共用领域规则。
3. UI 只提交命令与展示视图，不能直接改变境界、物品、关系、游戏时间或随机状态。
4. 时间与随机只能从项目接口获得；浏览器刷新、组件重绘和图片请求不结算游戏。
5. 命令有稳定 ID 与前置修订号，所有关联状态在完整事务中提交。
6. 规则结果、事件事实与当前交互进度同时保存，处理跨标签页冲突及重复消息。
7. 突破失败对玩家和 NPC 均非致命；真正死亡取消行动、保留历史身份。
8. AI 输出作为候选，不能执行其任意代码、HTML 或状态修改；用户文本与模型文本按安全文本渲染。
9. 图片使用合法资源引用，加载失败不重做规则结算；密钥不进入前端、存档或日志。
10. 修改数据结构或内容语义时处理版本和迁移，不静默重置存档。
11. 报告具体完成项、测试结果、未验证设备与剩余问题；不得虚构性能或兼容性结果。
12. 同时并行的任务需有清楚接口和文件边界；普通实现细节自行处理，产品缺口在实际依赖点提交具体方案。
