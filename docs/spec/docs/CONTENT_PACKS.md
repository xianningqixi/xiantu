# 剧情、插图与规则解耦：内容包补充规范

日期：2026-09-06。适用：V0.1.1-Web 执行包。状态：原架构规格保留；CP-01—03 已实现构建时内容登记、通用能力、隔离预览和独立第二作者包并通过本地验证。当前实现及兼容限制见 [本轮验收矩阵](../../reports/V01-LOCAL-ACCEPTANCE.md) 和 [作者流程](../../../content-packs/AUTHORING.md)。可视化编辑器仍延期。

目标：让剧情作者、美术和程序员能够分别交付成果。第一条官方人物故事也通过同一内容接口实现，验证以后其他作者能否独立增加故事。

## 1. 拆分什么

| 部分 | 负责的内容 | 与其他部分的连接 |
| --- | --- | --- |
| 世界设定基线 | 修仙世界共识、已有角色身份、境界与势力设定 | 官方资料与稳定定义 ID；内容作者可扩写，不能默默改写已有身份 |
| 规则引擎 | 时间、随机、修炼、战斗、生死、关系、承诺、资源与存档 | 提供有版本的条件查询和命令接口 |
| 剧情内容包 | 人物故事大纲、对白、触发条件、选择、分支、配图需求、新内容定义 | 引用角色、地点和视觉 ID；调用引擎已有能力 |
| 图片资源包 | 背景、立绘、表情、事件插图与展示规格 | 将视觉 ID 映射到图片、替代描述及角色身份 |
| 页面展示 | 排版、按钮、历史、图片加载、手机适配 | 渲染规则已确认的当前场景，不自行改变世界 |
| 运行存档 | 本局角色、经历、已展示正文、约定、关系、奖励领取、随机状态 | 锁定内容版本；不能写回静态剧情模板 |

剧情与图片可以独立制作、独立维护，也可以一起打进一个 ZIP 交付。初期使用同一个仓库的不同目录即可；解耦不要求立刻拆成多个仓库、服务或网站。

## 2. 大纲与可执行剧情分别保存

大纲描述主题、人物动机、预期分支和情绪变化，供创作与审阅使用。它不参与运行，也不能强制一个已经死亡或离开的 NPC 按原计划出场。

可执行事件必须描述：当前谁参与、何时可触发、显示什么、玩家可做什么、通过哪个合法命令产生后果、失去条件后如何回到正常游戏。

例如“大纲：林晚在秘境后因分赃而重新评价玩家”，转为事件时至少需要履约、违约、没有掉落约定物、NPC 不在场／死亡等状态。后果来自真实分配和知情事实；不能只写一句“她更加信任你”就完成关系结算。

作者可以用 Markdown 大纲及表格填写事件。V0.1 的可校验交付格式采用 JSON；表格或未来表单需要经过确定性转换和校验。AI 可协助整理草稿，但不能把未经核对的自然语言直接当世界规则执行。

## 3. 最小内容包结构

以下为待实现的目录约定，不表示这些目录和工具已生成。

| 路径 | 作者需要填写什么 |
| --- | --- |
| `manifest.json` | 包 ID、版本、内容协议、所需规则能力、精确依赖、入口清单、作者与许可 |
| `outline.md` | 故事大纲、人物动机、分支说明、世界设定约束 |
| `definitions.json` | 本包新增的角色／物品／地点模板，以及对已有定义的引用 |
| `storylets.json` | 对白、条件、选项、已有命令调用、跳转与重复限制 |
| `visuals.json` | 剧情需要的背景／立绘／事件插图槽位与角色、场景、表情约束 |
| `art/manifest.json` | 图片资源包 ID、版本、槽位映射、文件哈希、尺寸、替代文字和素材来源 |
| `art/images/` | 实际图片；制作阶段允许明确标记 planned 的占位 |
| `fixtures/` | 首见、履约、违约、缺席等作者预览状态，不能作为玩家真实存档入口 |
| `acceptance.md` | 可重现步骤、预期事件、实际资源后果及图片检查 |

清单中的 `packId`、`packVersion`、`contentApiVersion`、`requiresCapabilities`、`dependencies`、`entryFiles`、`author`、`license` 为第一版必填字段；具体 JSON Schema 在 CP-01 中落地。依赖在 V0.1 使用精确版本，发布时记录所有依赖的实际哈希；不通过网络加载任意脚本、URL 或未声明文件。

包 ID 使用作者或项目命名空间，例如 `official.lin_story`、`creator.wandering_doctor`。包内故事、事实、模板和视觉 ID 均属于该命名空间；重复注册或尝试覆盖其他包 ID 直接报错。现有 `NPC_LIN_WAN` 等旧 ID 通过官方包兼容映射保留，不能原地改名让历史引用断开。

## 4. 剧情与图片通过稳定视觉 ID 相连

故事声明“林晚的戒备表情”，不在正文中写文件路径。原型已有的 `portraitAssetIds`、`backgroundAssetId` 可继续作为视觉引用入口；资源解析层将这些 ID 对应到图片文件。

以现有 `PORTRAIT_LIN_GUARDED` 为例：

1. 剧情事件引用该 ID，继续绑定 `NPC_LIN_WAN`。
2. 资源表登记人物身份、戒备表情、裁切安全区、图片文件及替代描述。
3. 美术更新这张图时保持槽位语义和人物身份，并更新资源包版本与哈希。
4. 页面只更新展示；不重新抽事件，不重新发奖励，不改变信任。

同一张坊市背景可被多个故事引用，剧情也可复用官方人物图。新图片皮肤只能改变表现，不能把林晚的脸或姓名换给另一位 NPC。生成图片时的提示词、参考图和外貌 Seed 是制作资料；实际交付文件及其映射才是运行时依据。

缺图时保留文字、身份、替代说明和选项。作者预览允许 planned 资源；对外发布所需资源必须实际存在，或有明确列入发布范围的占位方案。图片是否像素风仍沿用已有美术决策，不因内容包机制另行改定。

## 5. 作者可以做什么

| 作者需求 | 实施边界 |
| --- | --- |
| 改对白、配图、分支排序 | 只修改本包数据；经过条件与引用校验 |
| 为一个新人写相识和同行 | 使用通用的相识、故事进度、约定等能力，绑定本局真实角色 |
| 增加角色、地点或物品 | 使用已支持的模板；由创建世界流程实例化，服从生成与引用约束 |
| 记录“已问过药材去向” | 使用本包声明的、有类型的故事局部状态，通过有效剧情命令提交 |
| 根据真实违约产生反应 | 查询世界已确认的事实与该 NPC 的知情来源，调用已有后果处理 |
| 加一个引擎没有的新玩法 | 提出所需能力，由程序员实现、测试并版本化后再调用 |
| 改突破致死、生死或任意关系数值 | 普通剧情包不具备这类权限；不得绕过共同规则 |

局部故事状态只描述本故事进度，不能冒充世界事实。将局部键命名为“已履约”“目标存活”等，不会使世界约定成立或角色复活。世界事实由领域规则提供只读投影；所有实际后果必须走命令校验与同一事务。

关键角色绑定必须固定：林晚专属故事绑定林晚；可复用的路人模板才允许按资格选人。选中的本局实体 ID 写入故事实例，刷新不能换人。角色不再符合条件时禁用或转入缺席分支，不能偷偷换个活人延续死者的故事。

## 6. 现有方案需要补的关键一层

当前 `storylets.json` 与 `assets.json` 已分开，正文也通过素材 ID 引用图片；这属于基础数据解耦。现有 `lin.*` 条件投影、专属 `Talk` 话题和固定人物模板仍有故事专用逻辑。如果新增一个角色仍需程序员增加一组专属处理器，就还未达到独立创作目标。

需要把已经证明有用的相识、领取知识、更新本包进度、提出约定与记录经历抽成有校验的通用能力。能力以参与者和范围作为参数，保留资源归属、在场、生死、去重及知情校验。内容包声明所需能力，引擎不支持时在加载前给出明确错误。

先由林晚故事和另一条小支线共同验证抽取是否足够；不提前设计任意脚本语言。不得用 `eval`、任意属性赋值、内容文件中的可执行 JavaScript，或者完全交给模型解释剧情，来替代这些接口。

## 7. 版本、存档与复现

新游戏确定启用包及依赖顺序，保存精确版本与哈希。相同 Seed 的复现承诺，必须同时固定规则版本、内容集合和生成算法。新增角色包导致初始世界变化是内容变化，不能声称只靠 Seed 就仍然相同。

运行存档持有已发生事件、已显示文本、故事实例及参与者、领取记录与包锁定信息。清单不会覆盖这些事实；剧情文件更新不能重置 NPC 记忆或重发奖励。

V0.1 先支持发布构建时登记内容包、新游戏选择固定包组合。进行中的存档不随意安装、卸载或自动升级包；新版本保留旧依赖以继续旧局。缺少必需包时保留原档并提示恢复对应版本，不清空本局或临时替换角色。

未来再实现作者 ZIP 导入、带显式迁移的内容升级和资源皮肤切换。资源纯展示也要记录采用的版本，不能在缺少旧图时阻断文字与行动。

## 8. 给作者的最小工作流程

1. 复制一个能工作的示例包，声明包名、依赖和使用的世界设定。
2. 写大纲，填写人物、事件、对白、选项和图片需求。
3. 美术按视觉 ID 独立交付资源；未完成时使用占位预览。
4. 运行包校验，错误显示文件、节点、字段和具体原因。
5. 使用作者预览依次检查首见、成功、违约、NPC 缺席／死亡、资源不足和图片缺失等状态。
6. 在正常游戏命令流程中走完一条合法路径，提交包与验证记录。

预览必须复用正式渲染器与规则入口，同时使用单独的测试世界。不能让预览界面绕过规则后把“可点通”当作游戏验收。不会编程的作者先获得模板、填写说明与本地预览命令；可视化编辑器以后基于同一协议制作。

## 10. 参考与验证范围

Ink 官方将叙事系统设计为可接入游戏引擎的中间件，Inky 支持编写、预览及导出；这支持“作者工具与游戏实现分工”的思路，不代表本项目必须迁移到 Ink。[Ink 官方介绍](https://www.inklestudios.com/ink/)

JSON Schema 能描述 JSON 结构、类型与约束，适合内容文件的结构校验；跨文件引用、剧情可达性、NPC 知情和实际资源结算仍需本项目的语义检查与运行测试。[JSON Schema 官方入门](https://json-schema.org/learn/getting-started-step-by-step)
